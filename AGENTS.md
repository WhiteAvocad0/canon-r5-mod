# Canon R5 Mod

Public source-preview project for original Canon EOS R5 firmware `2.2.1` only. Provides two separate offline-buildable profiles:

1. `shutter-feedback` (default): custom startup + shutter WAV speaker playback; immutable private reference is user-confirmed `build36` (`562,144` B, `3579cecf...`).
2. `xpan-crop` (experimental, silent by default): `2.71:1` (`512:189` ~ `2.709:1`) XPan crop mode (`8192x3024` Large JPEG, `8192x5464` CR3 crop `(0,1220,8192,3024)`, replaces `16:9`, Q `"XPan"` label, live LCD/EVF framing, playback masking). Prior private candidate `466ca8fe` (`c9f06053`) was user-confirmed on rear LCD landscape first-open playback (`DbgRA127`), live LCD/EVF, Q label, and saved crop output; earlier `128 GB` silent XPan (`1b7bfcfa`) + CFexpress coexistence was also confirmed; latest native reference `4838eb81` (`427bb28d`, `117` inputs, `31` hooks, `17` pages, `8` L2 tables, `120` witnesses, `948,152` free bytes, `184`B fit / `40`B view owner, `67` V1 reasons) extends playback masking to `(device in {0,1}, orientation in {0,2}, effective r7=0)` and was reported working in the owner's four-case normal ▶ session on 17 November 2026 (private research suite: `289` tests and independent reviews). The current public profile also carries the automatic post-shot review fix (immediate XPan bars, 16:9 outline hidden for XPan only; `34` hooks, `20` pages, `10` L2 tables, `137` witnesses), verified on private lab build `a7e92a3d` on 18 November 2026. The public image with `--record-indicator ding` (`05e9612`, `0adff001...`) passed a short owner check on 18 November 2026 (boot, live XPan framing, immediate XPan bars in automatic review, a Full-frame control and the REC `ding`); normal ▶ playback was not repeated on it.

- Distinguish source facts, host tests, and user-reported camera evidence. Private `xpan-crop` (`466ca8fe`) was user-confirmed for rear LCD landscape first-open, live LCD/EVF, Q label, and `RAW+Large JPEG` XPan capture; `4838eb81` normal ▶ portrait LCD/EVF playback was reported working in the four-case session on 17 November 2026; private `a7e92a3d` (18 November 2026, `128 GB` card) was reported working for XPan-only immediate automatic-review bars with the outline hidden, stock Full-frame review, burst and EVF, and the REC-press `ding`. Public repackaging and other qualities/modes/active auto-rotation remain unverified/declined.
- Do not commit or upload Canon ROM/FIR/dumps, built images/objects/toolchains, real diagnostic dumps/photos (`.CR3`/`.JPG`), user audio (XP/Mambo), generated Canon ROM pages/tables/vectors, credentials, build outputs, private lab history, or local plans. Users supply their own ROM dump (and two WAV clips for `shutter-feedback`). Publication is source+docs only, no binary release.
- Preserve native baseline C/ASM/linker behavior. All addresses are original R5 `2.2.1`-specific. Other R5 firmware/R5 C/R5 Mark II/R6/R6 II/R6 III are unsupported and need independent ports; no cross-model binary testing.
- No automatic camera-side BootDisk/bootflag activation, and no firmware/NVRAM writes, formatting, partitioning or MBR writes by any tool here.
- Setup wizard (owner decision, 18 November 2026): the GUI is a step-by-step wizard (`tools/gui/wizard.py` holds the widget-free step logic and saved progress in `~/.r5-build-assistant/wizard.json`; facts that can be re-checked are re-checked on resume). Its guided ROM-dump step (read-only) and guided BootDisk step are owner-approved and stay: never automatic, always run by the person in the camera from a Canon Basic card the app prepares within the cardprep safety framework (backup, confirm, read-back, undo), behind a required acknowledgement for BootDisk, verified by readback, with a "Disable BootDisk" path; the tool itself never writes the camera's firmware or NVRAM. Card instructions require backups and correct model/firmware. The CLI builder (`tools/build.py`) builds offline only and never writes cards.
- Canon Basic ROM dump and BootDisk (`tools/cardprep/cbasic.py`, FAT32 SDHC `<= 32 GB` only, `SDHC_MAX_SECTORS = 0x4000000`): Canon Basic uses `SCRIPT` at offset `0x1F0` (`496`) of the primary FAT32 boot sector (only when `0x1F0..0x1F6` is all-zero and no native `BOOTDISK` marker is present) plus `script.req` (`for DC_scriptdisk\n`) and `extend.m` at the card root, triggered by powering on in `▶` playback and pressing `SET`. On EOS R5 `2.2.1` (`System.Create` `0xE07407CA` registers `EnableBootDisk` `0xE0B38D62`, `DisableBootDisk` `0xE0B38D74`, `SaveAllRomImageToFile` `0xE0B38CD4`), the read-only ROM dump script calls `SaveAllRomImageToFile()` (writes `64 MiB` `gang100.bin` at `0xE0000000` and `16 KiB` `gang200.bin` BootInfo at `0xE8004000`); the BootDisk enable and disable scripts dump before (`gang100.bin`/`gang200.bin`), call `EnableBootDisk()` or `DisableBootDisk()`, wait `2000 ms`, and dump after (`gang101.bin`/`gang201.bin`). Readback verification (`cbasic.verify_bootinfo`, `checks.check_bootinfo`) checks exact `16,384`-byte size, exact `16,380` non-flag bytes against the camera's own `64 MiB` ROM mirror at `0xE0004000` (when a ROM is available) and any before-dump, and requires `u32_le(+0x04)` (`0xE8004004`) to equal `0x00000000` (`enabled`) or `0xFFFFFFFF` (`disabled`); any other value or mismatch is refused. Importing a returned card copies the dump to the user's computer with SHA-256 readback, validates the `64 MiB` ROM through `build.check_rom`, and renames `extend.m` / `script.req` on the card to `.done` so `SET` in `▶` playback will not re-run the script (`SCRIPT` at `0x1F0` remains until Undo or camera format). The `DisableBootDisk` script is derived from ROM disassembly (`0xE0B38D74` -> `0xE05E3E66(1)`) and is **hardware-untested**.
- Card boot markers (owner decision, 18 November 2026, issue #16 Phase 2): the GUI build assistant alone offers opt-in boot-marker preparation (`tools/cardprep/`, the "Prepare card" tab). It is the only raw-device writer. Keep its safeguards: an up-front warning to format in the camera first and copy photos off (advisory; the tool never formats, and the layout refusals are the real check); only removable SD cards in an SD slot are offered (no internal, boot or system disks, disk images, USB readers or sizes outside 2 GB-2 TiB); the person selects the card from that list and confirms one dialog naming it (owner UX decision 18 November 2026: no typed volume name, no separate backup step); before that dialog the MBR and the partition's first 24 sectors are backed up automatically to a new, never-reused, never auto-deleted timestamped folder and verified by re-reading; only the planned sectors are written (FAT32: `EOS_DEVELOP` at `0x47` and `BOOTDISK` at `0x5C` of the primary boot sector; exFAT: `BOOTDISK` `+122` and `EOS_DEVELOP` `+130` in both boot regions plus both checksum sectors per the Microsoft exFAT spec, backup region first), through a whitelist (`tools/cardprep/rawio.py`, partition sectors 0/11/12/23 only) that refuses unless the MBR, the whole boot area and the target sectors still hash to the planning read, and only after the partition start agrees three ways (MBR LBA×512, diskutil offset, boot-sector PartitionOffset/HiddenSectors); the card stays unmounted from that read to the write; every byte is read back and compared, `diskutil verifyVolume` runs, and the volume is unmounted (never ejected) and remounted; Undo/restore uses the same checks and works on an unmounted or half-written card (identified by disk and partition, not by a mount); every outcome, including timeouts, is reported with the backup path, never silent; one card operation at a time, also blocking the copy-to-card tab. Raw access uses macOS `authopen` only (`/usr/libexec/authopen -stdoutpipe -o <O_RDONLY|O_RDWR> /dev/rdiskN`, whole disk, one authorization window per step): it opens just that device and passes the descriptor over a UNIX socket (SCM_RIGHTS); the descriptor must be a character device with the chosen disk's `st_rdev` and the requested access mode, all I/O runs in-process at absolute offsets, and it is always closed. No code runs as root (an `osascript` root shell was denied raw access by macOS TCC on the owner's Mac); never ask for, store or pass a password. This cannot protect against malware already running as the user. Anything unexpected (unknown filesystem, geometry mismatch, MBR inconsistent with the volume, non-512-byte sectors, unexpected bytes where markers go) is refused. Only 512-byte-sector FAT32 and exFAT are handled. The macOS exFAT path was verified on 18 November 2026 on the owner's Mac (macOS 27.3) with a camera-formatted 128 GB card: sectors 12/23/0/11 written, read-back and verifyVolume passed, a second Prepare said Already prepared, and the camera booted the card (private lab build). FAT32 cards are untested; Windows/Linux offer untested detection only and no writes.
- Firmware admission must accept per-camera settings differences outside immutable target code while retaining strict exact-code/patch/table/resource checks (`config/target_contract.json`, `config/xpan_target_contract.json`). Preserve actual caller ROM digest and paths as provenance, not a private camera full-dump hash as compatibility identity. Derive ROM-backed XPan inputs (`target-page.bin`, `frame_row_constants.h`, `menu-vector.bin`, `feature-targets.h`) into `--output` only after strict target admission. No `--force` or skip-target-check option.
- Audio roles (`shutter-feedback` default): startup WAV and shutter WAV separate, full clips, 48kHz mono 16-bit PCM, 32-byte zero alignment only, no normalization/trimming. Busy effects drop; no delayed replay. No immediate user mute or full burst/movie/latency/shutdown certification claimed.
- XPan role (`--profile xpan-crop`): silent by default (`R5_CROP_ONLY=1`), forbids `--startup-wav`/`--shutter-wav`, links zero PCM/puff symbols, disables added shutter playback (`play_shutter = 0`) while retaining the headless control/report worker. Do not remove that worker; it maintains MMU/report state. Canon's own Beep setting is unchanged.
- Automatic post-shot review fix (always on in `xpan-crop`, no option): three cooperating hooks. `review_crop` at `0xE063FBEE` changes an exact full-source review descriptor tuple `{0,0,0,0,1024,682}` to `{0,152,0,152,1024,378}` (3 words); `xpan_authority` at `0xE054C530` passively records each shot's Job (signature `0xE2083738`, JobID `[obj+0x3C0]`, aspect `[obj+0x14C0]`, flags `[obj+0x19F0]`); `xpan_review_gate` with the outline hook at `0xE0A956FE` lets both act only for a fresh single-claim authority with aspect `7` and `(flags & 0x101) != 0`. Full frame and bursts (`MULTIPLE`) keep the stock review. Decisions are kept as `.bss` counters only; no report rows. Capacity is `CODE_PATCH_MAX 35`, `MULTI_MAX_PAGES 21`, `MULTI_MAX_TABLES 10`.
- Movie record indicator (issue #14, `--profile xpan-crop --record-indicator {off,ding,chirp2,2k150loud} --record-stop-indicator {off,dong}`, both default `off`, independent): opt-in only. Both `off` links no indicator code, hook, page or fingerprint check (`34/20/10/137`; with either or both cues `35/21/10/139`). Either cue adds the same one observer hook (`GUI_SetRecordingState` `0xE07C6FBC`, counters only: REC press `0->1` from LR `0xE0B0B883`; take ended = any idle `0` set after a confirmed `2->3` from LR `0xE0B0BD2D`), one deterministic integer cue per selected role generated once into its own 32-byte-aligned buffer by the worker (no WAV input, no user audio), a non-blocking `SE_BeepStart` step (SE id `2`; AudioCtrl mask `{1,4,5}` for the start cue and `{1,4}` for the stop cue, which waits out `5`; bounded busy retry and observe timeout, no late replay, one cue at a time, a new take drops a pending stop cue) and a minimal `R5T1` counter report. Its hook page and two guard pages are admitted only through `record_indicator_code_fingerprints`. The `ding` was user-tested on a private lab build and the public `ding` image `0adff001` played it in the 18 November 2026 owner check; the `ding` + `dong` private lab build `fbf31293` was owner-tested on 18 November 2026 ("confirmed that the dong works perfectly good"). The public `ding` + `dong` image `01956513` (built from `f4b2848`) passed a short owner check on 18 November 2026 (boot, live XPan framing, immediate review bars, a Full-frame control, the ding and dong over several takes, no dong in the played clip, the AF beep); `ding`-only and `dong`-only images from this version are new images and hardware-untested.

- Screenshots utility (`tools/screenshots.py`, GUI `tools/gui/shots.py`, outside the setup steps): converts the private lab build's `DCIM/R5SHOTS/SS_*.YCA` (R5SS v1/v2/v3 header, UYVA, 1024x682 LCD or 1600x1200 EVF only) to PNG with zlib/struct only, BT.601 full range like the lab converter. It only reads the card and source folder, refuses an output inside them or on the card's drive, and never overwrites a file. The on-camera screenshot build itself is a private lab feature, not in the public firmware build; say so. Tests use synthetic files only; never commit real screenshots.
- `config/features.json` (`tools/features.py`) is the single feature manifest: profiles, WAV input policies, options, profile dependencies and per-feature status. `tools/build.py` derives its selection CLI and rules from it, and the setup wizard (`tools/gui/`, standard-library Tkinter, issue #16) derives its feature checklist from it. The assistant builds through the CLI and copies only to an already-prepared card's folder (backup, temp-then-rename, SHA-256 readback); the copy step never formats, writes boot sectors or deletes anything but its own temp file. Boot sectors are written only by the separate "Prepare card" step described above.
- Host tests must run without private lab paths/assets or ARM toolchain. Real-ROM cross-build verification is separately opt-in and reported distinctly. Do not install unrelated software or dependencies automatically.
